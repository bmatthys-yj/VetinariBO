Use Vetinari’s published agent SDK in BO

Keep the Pappers instructions, tools, and company lookup policy in VetinariBO. Replace its hand-written model loop with the agent factory and LiteLLM provider published by Vetinari.

Implemented with the published packages

No Vetinari code change was needed. The downloaded 0.0.1 release contains createAgent, withAgentAttribution, and createLiteLlmModel. The published packages supplied the runtime and LiteLLM provider. BO now passes native ManagedVetinariAgent instances through its existing routes and lead queue.

Use an embedded agent in BO’s process. Call agent.generate() from the existing BO endpoints and lead researcher. This path requires no PostgreSQL service, Vetinari HTTP server, or running Acme application.

Implemented SDK composition

This shows the implemented integration shape. The provider reads its configuration from the standard LiteLLM environment variables. 

import { randomUUID } from "node:crypto";
import { z } from "zod";
import { createAgent, withAgentAttribution }
  from "@quinus-yj/vetinari-runtime";
import { createLiteLlmModel }
  from "@quinus-yj/vetinari-provider-litellm";
import { Mastra } from "@mastra/core/mastra";
import { createTool } from "@mastra/core/tools";

const model = createLiteLlmModel();

const agent = createAgent({
  id: "pappers",
  name: "Pappers company researcher",
  instructions: SYSTEM_PROMPT,
  model: model.languageModel,
  mastra: new Mastra({ logger: false }),
  tools: {
    search_companies: createTool({
      id: "search_companies",
      description: SEARCH_DESCRIPTION,
      inputSchema: searchCompaniesArgs,
      execute: async (args) => searchAndTrimSafely(pappersClient, args),
    }),
    // get_company follows the same pattern.
  },
});

const result = await withAgentAttribution({
  clientId: "vetinari-bo",
  agentId: "pappers",
  agentRunId: randomUUID(),
}, () => agent.generate(input, {
  maxSteps: 8,
  toolCallConcurrency: 1,
  abortSignal,
}));

// BO projects result.text and result.steps to its existing API DTO.

BO uses the native createTool() factory and inferred types through a direct @mastra/core@1.65.0 dependency. Mastra validates the existing Zod schemas before calling the Pappers client. A Mastra instance with logging disabled keeps raw provider failures out of SDK logs; routes and the lead queue redact the gateway key before showing or storing errors.

Acceptance checks and implementation risks
  • API compatibility: directory/detail metadata, valid run output, complete ordered tool history, malformed prompt 400, missing setup 503, unknown agent 404, safe run failure 502, and gateway model listing.
  • Agent behavior: no tool reply, multiple tool rounds, argument validation, unknown tools, recoverable tool failure, result truncation, abort/timeout, and eight-step exhaustion. Check actual finish reasons and SDK error chunks; do not assume the old runner’s failure behavior is automatic.
  • Cost: tool execution stays serial; per-run budgets do not silently gain extra retries. Eight steps limits model turns, not the number of tools a model requests in one turn; preserve the existing meaning rather than claiming an eight-tool-call cap.
  • Background lookup: valid profiles and not-found replies, invalid JSON/schema failures, skipped setup, retry, serial work, restart recovery, and continuation after a failed lookup.
  • Privacy and isolation: only company plus allowed employer domain enters lookup prompts; Pappers tokens never appear in DTOs/logs; public enrollment stays successful when research fails; public routes never expose backoffice agents or gateway.
  • Dependency/lifecycle: root imports from published package entrypoints work under NodeNext; no extra service starts are required for direct generation. The provider registers no closeable resources. Pin releases because this SDK is currently 0.0.1.

Use test/agents.test.ts, test/leads.test.ts, and test/isolation.test.ts for focused regressions. Run a controlled live lookup only if explicitly authorized; normal validation stays network-free. This research did not execute a live agent or paid API request.

What Vetinari could add later

Required for this migration: nothing. The downloaded SDK already exposes the factory, model, attribution, and native execution surface needed for local Pappers tools.

  • Documentation improvement: add an external, SQLite-backed app recipe showing direct createAgent().generate(), structural tools, setup gating, per-run limits, tool-result projection, and withAgentAttribution to docs/sdk-guide.md and package READMEs.
  • Optional authoring helper: add a deliberately supported tool factory/subpath if several external clients need type inference without a direct Mastra import. Update export maps, public surface inventory, package-path usage coverage, docs, and a Changeset before releasing it.
  • Optional package split: provide a small agent-authoring entrypoint/package if the runtime’s PostgreSQL/editor/observability dependency footprint becomes a problem. Avoid making BO wait for that refactor.

A shared Pappers package is outside the selected scope: its instructions and tools remain in BO. Full Vetinari transport, Console, Studio, workflow persistence, and authentication can be separate features if needed.

Registry audit also found @quinus-yj/vetinari-migrations returning 404. It is not needed for this plan; verify its publishing/access separately before any future PostgreSQL or persisted-runtime adoption.
