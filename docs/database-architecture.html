VetinariBO · system map

One Node process. Two doors. One SQLite file.

The backoffice SPA and public enrollment form reach the same database through separate HTTP apps. The browser never connects to SQLite directly.

Application structure

Who talks to what · swipe to explore on narrow screens

browser Node / Hono persistence external API

The backoffice app binds to loopback by default. The public app has its own routes and port; it shares the database handle, not the backoffice routes.

What happens to database data

Four common paths

Admin manages a workshop

React→/api→workshops repo→workshops

Rows are mapped to shared camelCase contracts before they reach the UI.

Attendee enrolls

form POST→public route→transaction→enrollment + lead

Seat checks, duplicate checks, lead linking, and the insert happen together.

New company is researched

lead queued→Pappers agent→profile saved→leads

Research status and the returned company profile are stored on the lead.

Erase an enrollment

admin request→enrollments repo→delete row

Lead records are managed separately, since one lead can link to several enrollments.

SQLite tables

Current data model

workshops

Workshop details, dates, capacity, and the unique enrollment-form slug.

enrollments

Attendee details and consent. workshop_id points to a workshop; lead_id links to a company lead when applicable.

leads

Unique attendee email, company, research status, and optional saved profile JSON.

Kysely provides typed queries. A small custom dialect connects it to Node’s built-in synchronous SQLite driver; repositories are the mapping boundary between SQL rows and API contracts.
